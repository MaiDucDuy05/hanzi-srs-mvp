## 1. Yêu cầu nghiệp vụ

Admin tìm kiếm, xem chi tiết, khoá/mở tài khoản và gán vai trò cho người dùng.

### 1.1. Luồng quản lý người dùng

1. Admin vào Dashboard → menu "Quản lý người dùng".
2. Trang danh sách hiển thị bảng:
   - Cột: Avatar, Tên, Email, Role, Trạng thái (Active/Banned), Ngày đăng ký, Hạn VIP.
   - Filter: Theo role (Free, VIP, Teacher, Admin), trạng thái, khoảng ngày đăng ký.
   - Search: Tìm theo tên hoặc email (full-text).
   - Pagination: 20 user/trang.
3. Click vào user → Trang chi tiết:
   - Thông tin cá nhân (read-only): Tên, Email, SĐT, Ngày đăng ký.
   - Vai trò hiện tại + dropdown đổi vai trò.
   - Trạng thái VIP: Hạn đến ngày nào (nếu có).
   - Lịch sử hoạt động gần đây: 10 hành động cuối (login, làm bài, nộp bài...).
   - Nút hành động: Ban / Unban, Đổi vai trò.

### 1.2. Luồng Ban/Unban

1. Admin bấm "Khóa tài khoản" → Popup nhập lý do (bắt buộc).
2. Xác nhận → Trạng thái user chuyển thành `BANNED`.
3. User bị ban khi đăng nhập sẽ nhận response lỗi: `"Tài khoản đã bị khóa. Lý do: {reason}. Liên hệ admin."`.
4. Token hiện tại của user bị ban sẽ bị invalidate (thêm vào blacklist hoặc revoke).
5. Unban: Admin bấm "Mở khóa" → User đăng nhập lại bình thường.

### 1.3. Luồng đổi vai trò

1. Admin chọn vai trò mới từ dropdown: Free, VIP, Teacher, Admin.
2. Popup xác nhận: "Bạn muốn đổi vai trò của {userName} từ {oldRole} sang {newRole}?"
3. Xác nhận → Cập nhật role.
4. Nếu đổi từ VIP → Free: Xóa `vip_valid_until`.
5. Nếu đổi sang VIP: Yêu cầu nhập thời hạn (30/180/365 ngày).
6. Nếu đổi sang Admin: Yêu cầu xác nhận 2 lần (double confirm).

### 1.4. Quy tắc chính

* Tất cả thao tác quản trị phải ghi audit log (ai làm, lúc nào, thay đổi gì).
* Admin không được tự ban chính mình.
* Admin không được tự hạ role của chính mình (phải nhờ admin khác).
* Admin không xem được mật khẩu, refresh token hoặc API key dạng plain text.
* Tối thiểu phải có 1 tài khoản Admin trong hệ thống (không cho phép xóa/hạ admin cuối cùng).

## 3. Triển khai Backend — NestJS

### 3.1. Cấu trúc module

```text
admin/
  admin-users.controller.ts
  admin-users.service.ts
  audit-log.service.ts
  guards/
    admin.guard.ts
  dto/
    query-users.dto.ts
    ban-user.dto.ts
    change-role.dto.ts
```

### 3.2. API cần triển khai

| Method | Endpoint | Chức năng |
| :--- | :--- | :--- |
| GET | `/api/admin/users` | Danh sách user (filter, search, pagination) |
| GET | `/api/admin/users/:id` | Chi tiết user |
| PUT | `/api/admin/users/:id/role` | Đổi vai trò |
| POST | `/api/admin/users/:id/ban` | Khóa tài khoản |
| POST | `/api/admin/users/:id/unban` | Mở khóa |
| GET | `/api/admin/audit-logs` | Lịch sử thao tác admin |

### 3.3. Guard Admin

```typescript
@Injectable()
export class AdminGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const user = context.switchToHttp().getRequest().user;
    return user?.role === 'ADMIN';
  }
}
```

Tất cả API `/api/admin/*` đều áp dụng `@UseGuards(AdminGuard)`.

### 3.4. Luồng Ban với token invalidation

1. Cập nhật `users.status = BANNED`, lưu `ban_reason`, `banned_by`.
2. Thêm `userId` vào Redis blacklist (key: `banned:{userId}`, TTL = thời hạn token).
3. Auth middleware kiểm tra blacklist trước khi xử lý request.
4. Ghi audit log.

### 3.5. Xử lý lỗi

* Ban chính mình: `CANNOT_BAN_SELF`.
* Hạ role admin cuối cùng: `LAST_ADMIN_PROTECTED`.
* User không tồn tại: 404.
* Không phải admin: 403.

## 6. Tiêu chí hoàn thành

PR-27 được nghiệm thu khi:

* Admin tìm kiếm user theo tên/email, filter theo role/status.
* Ban user thành công, user bị ban không đăng nhập được và nhận thông báo lý do.
* Token user bị ban bị invalidate ngay lập tức.
* Đổi vai trò hoạt động đúng, kèm xử lý logic VIP (thêm/xóa hạn).
* Không thể ban chính mình hoặc hạ role admin cuối cùng.
* Mọi thao tác admin được ghi audit log.
* Admin không xem được mật khẩu/token dạng plain text.
